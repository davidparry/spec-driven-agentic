What changes in the agentic era?

Stays the same

  • Red/Green/Refactor cycle
  • Tests define "done"
  • Human owns every engineering decision

Gets amplified

The spec is a catalog

requirements/requirements.json is always the entry point, but need not hold every requirement: it carries its own requirements plus an includes list of child spec files, N levels deep.


requirements/
├── requirements.json      ← the catalog: own requirements + includes
├── core/
│   ├── arithmetic.json    ← included by the root
│   └── edge-cases.json    ← included by arithmetic.json (nesting!)
└── validation/
    └── negatives.json     ← included by the root
  • Tooling merges the tree depth-first into one backlog — list_requirements, validate_spec, and the agents all drive from the merged view
  • Ids stay unique across the whole tree; cycles and missing files are validation issues, not crashes
  • Mutations write back to the file a requirement lives in

The answer is not a bigger model. It is a narrower job.

Build the harness, not the prompt

A purpose-built harness is software that already knows the job. The model is one component in it — and it can be the smallest one that still works.

The harness owns

  • The sequence — spec → Gherkin → RED → GREEN → REFACTOR, in that order, every run
  • The tool surface — a handful of typed tools per step, never a shell
  • The gates — no refactor off green, nothing implemented without a tagged scenario
  • The prompts — one auditable file, versioned with the code

The model is left with

  • Word one requirement
  • Turn accepted criteria into a scenario and a test
  • Write the simplest code that turns the bar green

Jobs a model on your laptop can do — because nothing is asking it to remember the discipline.

Frontier capability buys slack. A harness means you do not need the slack.

The missing piece: a protocol

For an agent to run your tests and respect your workflow, it needs a standard way to discover and call your tools.

That standard is the Model Context Protocol.

Think "USB-C for AI tooling": one connector, any host, any tool.

MCP architecture


+-----------------------------+          +---------------------------+
|  HOST (Cursor, Claude, ...) |          |  MCP SERVER (yours!)      |
|                             |  stdio / |                           |
|   +---------------------+   |   HTTP   |  25 tools                 |
|   | MCP CLIENT          |<--+----------+>  resources               |
|   | (one per server)    |   | JSON-RPC |  prompts                  |
|   +---------------------+   |   2.0    |                           |
|            ^                |          +---------------------------+
|            |                |
|         LLM agent           |
+-----------------------------+
  • Host embeds an LLM and one MCP client per connection

The wire: JSON-RPC 2.0

Three message types: requests (have an id), responses, notifications (no id).


{ "jsonrpc": "2.0", "id": 1, "method": "initialize",
  "params": { "protocolVersion": "2025-11-25",
              "capabilities": { },
              "clientInfo": { "name": "tdd-workshop-agent", "version": "1.0.0" } } }
      

{ "jsonrpc": "2.0", "id": 1,
  "result": { "protocolVersion": "2025-11-25",
              "capabilities": { "tools": { "listChanged": true }, "logging": { } },
              "serverInfo": { "name": "spec-driven-server", "title": "Spec Driven", "version": "1.0.0" },
              "instructions": "Drives a spec-driven TDD/BDD workflow..." } }

The server — already built

One binary: spec mcp serve --root ${workspaceFolder}. Twenty-five tools in three groups:

  • Frozen seven — list_requirements, get_requirement, validate_spec, refine_requirement, run_tests, get_tdd_state, start_refactor
  • Authoring / staging — features, scenarios, changes_*, requirement_mark_implemented, template-only step_definition_create / unit_test_create
  • Inspect — project_root, project_inspect, command_run (allowlisted, RED-gated)

A stdio server must never print to stdout — that corrupts the JSON-RPC stream. Diagnostics go to stderr.

Anatomy of a tool — what the agent sees

One entry from tools/list — see them all with spec mcp tools:


{ "name": "get_requirement",
  "description": "Get the user story and acceptance criteria for one requirement. Turn each acceptance criterion into a failing test before writing production code.",
  "inputSchema": { "type": "object", "required": ["id"],
    "properties": { "id": { "type": "string", "description": "The requirement id, e.g. REQ-003" } } } }
  • Name, schema, description → the API docs the LLM reads at discovery. Writing them well is prompt engineering
  • Failures come back as results with isError: true, so the agent reads them and recovers

The tool that closes the loop: run_tests


agent  →  tools/call   run_tests   { }
      

{ "phase": "RED",
  "lastRun": { "tests": 8, "failures": 2, "errors": 1, "skipped": 0 },
  "nextStep": "make the failing tests pass — do not refactor on RED" }

The agent calls it, not you — the prompt forbids claiming a pass without it. phase is the bar color; nextStep the next legal move. start_refactor refuses on any bar but GREEN.

The runner, concretely

One binary over those tools, doing one job. Each command is handed only the tools that job needs:


spec tools profiles        # spec-draft 4 · spec-reword 3 · scenario-generate 3
                          # steps-generate 4 · unittest-generate 4
                          # implement-advice 5 · implement 7 · refactor 5
                          # status 7 · ask 12 (read-only)
spec mcp call get_tdd_state  # inspect only — the agent is the normal caller
spec draft …          # lookup of disk catalog; parse_proposals_checked is the gate
spec implement REQ-003     # run_tests sees the working tree; command_run asks you first
spec ask "what is pending?"
  • Ten profiles, one per job — narrowed to the work in front of the model
  • Drifting local model? [tool_rules] in the prompts file
  • Cucumber does the spec half: an executable contract that predates all of this by twenty years

The spec is the entry ticket

Nothing gets written until the spec survives two deterministic reviews.

"Add a requirement to requirements/requirements.json: a custom delimiter may be declared on the first line, so //+\n1+2 adds up to 3. Then call validate_spec and fix every issue. Then call refine_requirement and reword from the findings until there are none. No scenarios, no code yet."
  • validate_spec owns structure — unique id, a real user story, criteria phrased Given/When/Then
  • refine_requirement owns wording — rejects "should", "handle", "quickly", stories with no why, happy-path-only coverage
  • Neither is a model call — both are deterministic

Draft the spec with your agent

The spec comes first — and the agent helps write it, then refine it. Prompt your IDE agent:

"Add a new requirement to requirements/requirements.json: a custom delimiter may be declared on the first line, so //+\n1+2 adds up to 3. Follow the existing format — unique id, title, user story, acceptance criteria phrased Given/When/Then, status pending. Then call validate_spec and fix every issue until the spec is valid. Then call refine_requirement on the new requirement and reword it from the findings until there are none. Do not write scenarios or code yet — we are only agreeing on the spec."
  • The agent drafts, the server critiques, the agent rewords — you approve the final wording

The spec iteration loop — two stages

youdescribe the feature in a sentence of intent
agentdrafts the requirement into requirements.json
structurevalidate_spec → "criterion must be phrased Given/When/Then" → agent fixes → "valid": true
wordingrefine_requirement → "'quickly' is ambiguous", "only happy paths — add an edge case" → agent rewords → validates → refines → "clean": true
youread the story and criteria aloud — is this what we meant? Approve.

A valid, clean, approved spec is the entry ticket — no scenario or code before it.

Spec to green, Wi-Fi off

REQ-003, approved requirement to green bar — every mutation staged and reviewed.

"Using the spec-driven-server tools: validate_spec first, then get_requirement for REQ-003 — not the REQ-007 we just drafted. Add its Gherkin with scenario_add (tag the requirement id), add missing steps with step_definition_create if step_definitions_find reports any, add a unit test with unit_test_create. Show changes_show and wait before changes_commit. Then run_tests (expect RED). Implement the simplest production code in StringCalculator. run_tests (GREEN). start_refactor if I agree. On GREEN, requirement_mark_implemented."
  • RED Cucumber and JUnit come back as one bar — the agent does not get to guess
  • GREEN the simplest passing implementation, then start_refactor
  • requirement_mark_implemented needs GREEN and a scenario tagged with the id

Spec to green, agentically

Wire the server into your IDE agent:


// .cursor/mcp.json  (already in the repo)
{
  "mcpServers": {
    "spec-driven-server": {
      "command": "spec",
      "args": ["mcp", "serve", "--root", "${workspaceFolder}"]
    }
  }
}

Then prompt the agent:

"Using the spec-driven-server tools: validate the spec first, then get_requirement for REQ-003 — not the REQ-007 you just drafted, which stays pending until homework. Add its Gherkin with scenario_add (tag the requirement id), add missing steps with step_definition_create if step_definitions_find reports any, add a unit test with unit_test_create. Show changes_show and ask me before changes_commit. Then run_tests (expect RED). Implement the simplest production code in StringCalculator. run_tests (GREEN). start_refactor if I agree. On GREEN, requirement_mark_implemented. Ask me before each phase change."

The same requirement, a step at a time

That contract, driven by hand. No one-command orchestrator on stage — we are the orchestrator, so every check is one you watch fire.


spec status                       # asset survey: what REQ-003 lacks, and the next step
spec scenario add --req REQ-003 … # staged, tagged @REQ-003
spec steps missing                # [] — every wording is already bound
spec unittest generate REQ-003    # staged
spec changes show                 # checkpoint 1 — the staged Gherkin and test
spec changes commit
spec test                         # RED: 9 tests, 4 failures
spec implement REQ-003            # the model attempts; the diff is staged
spec changes show                 # checkpoint 2 — the production diff
spec changes commit && spec test  # GREEN: 9 tests, 0 failures
spec mark-implemented REQ-003     # refuses off GREEN, or with no tagged scenario
  • Checked, not trusted: spec status re-reads the assets on disk between steps — the step says it wrote a scenario, the survey says whether one is there
  • Two human checkpoints, both a diff: nothing reaches the working tree unreviewed
  • An IDE agent calling the tools lands in the same place — same gates, same bar, same checks next

Grade the run — seven checks, by name


scripts/verify-workshop-run.sh check
      

  PASS  REQ-007 was drafted into the spec
  PASS  the spec is valid
  PASS  REQ-007 wording is refine-clean
  PASS  REQ-007 covers the first-line delimiter declaration
  FAIL  REQ-003 status is 'implemented' in the spec - status is pending - Exercise 2 takes REQ-003, not the REQ-007 you drafted
  FAIL  @REQ-003 scenarios cover every acceptance criterion (0 tagged, 2 criteria) - no scenario is tagged @REQ-003
  FAIL  REQ-003 unit test asserts every acceptance criterion (0 @Test naming REQ-003) - no @Test names REQ-003

Three FAILs and nothing is broken: the whole Red/Green/Refactor arc ran on REQ-007 — pending, and the freshest thing in the agent's context. Every gate fired in the right order, because nothing was out of order.

The same script grades either surface — the agent over the 25 tools, or the harness a step at a time. Four checks on the requirement you drafted, three on REQ-003, each named rather than diffed against a recorded solution.

Why this works reliably

  • Valid spec first: validate_spec gates the pipeline — no scenario or code from a broken spec
  • Ground truth: the agent doesn't guess whether code works — run_tests tells it
  • Guardrails in tools: refactor-on-red is impossible; the server refuses
  • Small steps: one requirement, one cycle — failures stay cheap
  • Portable: one server, any host
The model supplies System 1. The tools and the human supply System 2.

A local model needs the loop

Not breakage — iteration. The model veers, a deterministic tool refuses, and the next attempt is better briefed.

What the model didWhat the harness did
Wrapped required JSON in fences, emitted <think> blocksRefused it and re-asked, the bad reply attached
Rewrote production code repeatedly — the real bug was a step expression missing a periodScanned the failures for implicated files; the reply must include them
Dropped an acceptance criterion while rewordingOne finding per call, and every criterion must come back
Repeated an attempt that had already failedBriefed the next prompt with what it wrote and what the run said
Implemented the next requirement too — bar greenMatched it against the other pending requirements and warned

What the loop cannot do: stop a loose host editing the test to force green, or tell you the requirement was worth the hour — the gates police how an agent works, never what it works on.

Without a runner: start free on pi

pi is a minimal, MIT-licensed coding agent. Ollama is a first-class provider. No account, no API key, no network.


// ~/.pi/agent/models.json
{ "providers": { "ollama": {
    "baseUrl": "http://127.0.0.1:11434/v1",
    "api": "openai-completions", "apiKey": "ollama",
    "models": [ { "id": "qwen3.8-flash-next:125b-mlx" } ] } } }

// ~/.pi/agent/settings.json
{ "defaultProvider": "ollama", "defaultModel": "qwen3.8-flash-next:125b-mlx" }
      

ollama pull qwen3.8-flash-next:125b-mlx
pi --offline            # or PI_OFFLINE=1 — no startup network calls at all

pi's philosophy, in pi's own words

"Pi is aggressively extensible so it doesn't have to dictate your workflow."
"No MCP."   "No permission popups."   "No sub-agents."   "No plan mode."   "No built-in to-dos."   "No background bash."
  • Eight built-in tools — among them bash, write, and edit
  • MCP is not in core — a third-party extension adds it

A deliberate engineering trade, not a defect — and the trade you inherit the moment the workflow is yours to supply.

Same model, no shell: pi --no-builtin-tools


pi install npm:pi-mcp-extension     # pi has no MCP in core — this adds it
      

// .pi/mcp.json — already committed in this repo
{ "mcpServers": { "spec-driven-server": {
    "transport": "stdio", "command": "spec", "args": ["mcp", "serve"],
    "lifecycle": "eager" } } }
      

pi -nbt          # built-ins off, extension tools stay on
                 # tools arrive as mcp_spec_driven_server_<tool>

No bash. No write. No edit. The same twenty-five tools the runner drives — and nothing about the model changed.

The server is the constant: spec, Cursor, and pi -nbt all call these tools.

General agent, or spec-specific runner?

What changes is how much of the workflow you have to supply yourself.

spec — spec-specific runner

  • Does one job: spec → Gherkin → RED → GREEN → REFACTOR
  • The workflow is already encoded: per-command profiles, staging, phase gates
  • Prompts live in one auditable file, not in your head

pi — general agent harness

  • Works on any task, which is the point
  • The workflow is yours to build: prompts, --skill, prompt templates, extensions
  • -nbt is a flag on one run — you re-supply it, and the sequencing, every time
The question is whether the discipline is something you re-type or something that ships.

What to take away

  • Build a harness, not a prompt: the sequence, the tool surface, and the gates belong in software you can version and audit
  • Tool surface beats model size: narrow the job far enough and a model on your laptop does work you would sign your name to
  • A prompt is a suggestion; a tool that refuses is a guarantee — no refactor off green, nothing implemented without a tagged scenario
  • The frontier model stops being the requirement: no key, no bill, no code leaving the building, and the same run reproducible in six months
