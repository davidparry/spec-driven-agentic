What changes in the agentic era?

Stays the same

  • Red/Green/Refactor cycle
  • Tests define "done"
  • Human owns every engineering decision

Gets amplified

  • Spec authoring: you describe intent, the agent drafts the requirement, tools validate and critique it
  • Requirements → tests: agents draft failing tests from acceptance criteria
  • Green phase: a developer agent proposes the implementation
  • Feedback loop: tools report bar color back to the agent automatically
The agent turns the crank. You steer.
Key framing: agents don't replace the discipline — they make the discipline cheaper to follow. The failing test becomes the contract between human and agent.

Three altitudes, one discipline

PinsCanonical artifactIn this repo
SDD spec-driven the featureversioned spec + acceptance criteria requirements/requirements.json
BDD behavior-driven one behaviorGherkin scenario (Given/When/Then) features/string_calculator.feature via Cucumber
TDD test-driven one unitfailing JUnit test StringCalculatorTest.java
  • Same "specify first" idea at three levels — they stack, they don't compete
  • Agentic SDD: the spec is the source of truth; agents generate scenarios, tests, and code from it
  • Our run_tests tool runs Cucumber + JUnit together: one bar, one color
TDD pins the unit. BDD pins the behavior. SDD pins the feature.
Key research-backed point: BDD/Gherkin is the direct ancestor of modern spec-driven development; what's new is that agents now write the glue and the implementation. In our workshop the acceptance criteria are already Given/When/Then — the agent's first job is turning them into executable Gherkin.

The spec is a catalog

requirements/requirements.json is always the entry point — but it doesn't have to hold every requirement itself. It carries its own requirements plus an includes list of child spec files, and children can include further files, N levels deep.


requirements/
├── requirements.json      ← the catalog: own requirements + includes
├── core/
│   ├── arithmetic.json    ← included by the root
│   └── edge-cases.json    ← included by arithmetic.json (nesting!)
└── validation/
    └── negatives.json     ← included by the root
  • Tooling merges the tree depth-first into one backlog — list_requirements, validate_spec, and the agents all drive from the merged view
  • Ids stay unique across the whole tree; cycles and missing files are validation issues, not crashes
  • Mutations write back to the file a requirement lives in — the kata fits in one file; real backlogs don't
This is the scaling story for SDD: one fixed entry point (requirements.json), a hierarchy of included spec files behind it. Cucumber never reads any of these — the spec drives the tooling, the tooling drives the Gherkin. Note the parallel to how big Gherkin suites split into many .feature files.

The missing piece: a protocol

For an agent to run your tests, read your requirements, and respect your workflow, it needs a standard way to discover and call your tools.

That standard is the Model Context Protocol.

Think "USB-C for AI tooling": one connector, any host (Cursor, Claude, your own client), any tool.

Transition to MCP fundamentals. Without a protocol, every IDE×agent×tool pairing is a custom integration.

MCP architecture


+-----------------------------+          +---------------------------+
|  HOST (Cursor, Claude, ...) |          |  MCP SERVER (yours!)      |
|                             |  stdio / |                           |
|   +---------------------+   |   HTTP   |  tools:                   |
|   | MCP CLIENT          |<--+----------+>  list_requirements       |
|   | (one per server)    |   | JSON-RPC |   get_requirement         |
|   +---------------------+   |   2.0    |   validate_spec           |
|            ^                |          |   refine_requirement      |
|            |                |          |   run_tests               |
|         LLM agent           |          |   get_tdd_state           |
+-----------------------------+          |   start_refactor          |
                                         +---------------------------+
  • Host embeds an LLM and one MCP client per connection
  • Server exposes tools, resources, and prompts
  • Transports: stdio (today) or Streamable HTTP
Both boxes are complete and in the repo — the right-hand box is our server, the left-hand box is any agent you like: Cursor, Claude, or the bundled CLI client. Today we use them; the code is there to read afterward.

The wire: JSON-RPC 2.0

Three message types: requests (have an id), responses, notifications (no id).


{ "jsonrpc": "2.0", "id": 1, "method": "initialize",
  "params": { "protocolVersion": "2025-11-25",
              "capabilities": { },
              "clientInfo": { "name": "tdd-workshop-agent", "version": "1.0.0" } } }
      

{ "jsonrpc": "2.0", "id": 1,
  "result": { "protocolVersion": "2025-11-25",
              "capabilities": { "tools": { "listChanged": true }, "logging": { } },
              "serverInfo": { "name": "spec-driven-server", "title": "Spec Driven", "version": "1.0.0", "description": "Serves spec-driven TDD and BDD tools. The requirements spec is the source of truth.", "websiteUrl": "https://davidparry.github.io/spec-driven-agentic/", "icons": [{ "src": "https://davidparry.github.io/spec-driven-agentic/assets/bdd-cli-mark.png", "mimeType": "image/png", "sizes": ["1024x1024"], "theme": "dark" }] },
              "instructions": "Drives a spec-driven TDD/BDD workflow..." } }
The handshake negotiates protocol version and capabilities. The server's "instructions" field is prompt text the host may feed to the LLM — we use it to teach the agent our workflow.

Lifecycle of every MCP session

  1. initialize — version + capability negotiation
  2. notifications/initialized — client says "ready"
  3. tools/list — discovery: what am I allowed to do?
  4. tools/call — invocation: do it
  5. Repeat 3–4; notifications flow both ways (logging, list changes)

Discovery is the superpower: the agent adapts to whatever tools the server offers — no hardcoding.

Emphasize: tool descriptions and JSON schemas ARE the API docs the LLM reads. Writing them well is prompt engineering.

PLUMBING The server — already built 13–20 min

One binary: bdd mcp serve --root ${workspaceFolder}. Composition root cli/src/mcp.rs plus the CLI TDD services. Twenty-four tools in three groups:

  • Frozen seven — list_requirements, get_requirement, validate_spec, refine_requirement, run_tests, get_tdd_state, start_refactor
  • Authoring / staging — features, scenarios, changes_*, requirement_mark_implemented, template-only step_definition_create / unit_test_create
  • Inspect — project_root, project_inspect, command_run (allowlisted, RED-gated)

A stdio server must never print to stdout — that corrupts the JSON-RPC stream. Diagnostics go to stderr. Wire identity is spec-driven-server / 1.0.0 (title Spec Driven).

Do not linger — this is infrastructure, not the point of the hour. There is no spec_draft or implement MCP tool. Attendees see all 24 in Cursor. The CLI path later offers 3–7 per command.

Anatomy of a tool — what the agent sees


#[tool(
    description = "Get the user story and acceptance criteria for one requirement. \
    Turn each acceptance criterion into a failing test before writing production code."
)]
async fn get_requirement(
    &self,
    Parameters(params): Parameters<IdParam>,
) -> Result<CallToolResult, McpError> {
    match self.spec_service().get_requirement(&params.id) {
        Ok(requirement) => json_result(&requirement),
        Err(e) => error_result(&e.0),
    }
}
  • Name + JSON Schema + description → the API docs the LLM reads at discovery
  • Handler → the same CLI services; return content + isError
  • This is how MCP feeds your tools into whatever agent your team uses
The one MCP idea worth two minutes: descriptions double as agent guidance. Tool errors are results with isError=true, not protocol errors — the agent reads and recovers.

The tool that closes the loop: run_tests


// TddService::run_tests — Maven / cucumber-js / dotnet / cargo
let report = tdd.run_tests(runner, &TestFilter::default())?;
// failures -> RED, all pass -> GREEN
// body.phase is the bar color the agent literally sees
// body.nextStep coaches the next legal move

The TddStateMachine in cli/src/domain/tdd.rs enforces the discipline: start_refactor refuses unless the bar is GREEN. requirement_mark_implemented is GREEN-gated too. Conformance: cli/tests/mcp_conformance.rs.

This is the workshop thesis in one slide: the workflow rules live in the tool, so any agent that connects inherits the discipline.

EXERCISE 1 Draft the spec with your agent 20–32 min

The spec comes first — and the agent helps write it, then refine it. Prompt your IDE agent:

"Add a new requirement to requirements/requirements.json: a custom delimiter may be declared on the first line, so //+\n1+2 adds up to 3. Follow the existing format — unique id, title, user story, acceptance criteria phrased Given/When/Then, status pending. Then call validate_spec and fix every issue until the spec is valid. Then call refine_requirement on the new requirement and reword it from the findings until there are none. Do not write scenarios or code yet — we are only agreeing on the spec."
  • Two feedback loops: validate_spec owns structure, refine_requirement owns wording quality
  • The agent drafts, the server critiques, the agent rewords — you approve the final wording
  • The kata's backlog fits in the root catalog; a real one splits into included spec files — same loop, same entry point
The heart of the hour: requirements gathering with an AI pair, with the server as the critic. Stage 1 validity is table stakes; stage 2 is where it gets interesting — the refiner flags "should", "handle", "quickly", stories missing their why, outcomes with no concrete value, happy-path-only criteria. Watch the LLM reword against deterministic feedback.

The spec iteration loop — two stages

youdescribe the feature in a sentence of intent
agentdrafts the requirement into requirements.json
structurevalidate_spec → "criterion must be phrased Given/When/Then" → agent fixes → "valid": true (a well-formed draft is often valid on the first call — force an issue to demo the loop)
wordingrefine_requirement → "'quickly' is ambiguous", "only happy paths — add an edge case" → agent rewords → validates → refines → "clean": true
youread the story and criteria aloud — is this what we meant? Approve.

The server re-reads the file on every call, so the spec the agent just wrote is the spec that gets critiqued. A valid, clean, approved spec is the entry ticket — no scenario or code before it.

Division of labor: the human owns intent, the agent owns wording and iteration speed, the server owns the feedback — deterministic, repeatable, no vibes. The LLM refining its own spec against tool feedback is the exact shape of the code loop coming next: write, check, fix, repeat.

EXERCISE 2 Spec to green, agentically 32–52 min

Wire the server into your IDE agent (Cursor shown; Claude Desktop is identical JSON):


// .cursor/mcp.json  (already in the repo)
{
  "mcpServers": {
    "spec-driven-server": {
      "command": "bdd",
      "args": ["mcp", "serve", "--root", "${workspaceFolder}"]
    }
  }
}

Then prompt the agent:

"Using the spec-driven-server tools: validate the spec first, then get_requirement for the next pending id. Add its Gherkin with scenario_add (tag the requirement id), add missing steps with step_definition_create if step_definitions_find reports any, add a unit test with unit_test_create. Show changes_show and ask me before changes_commit. Then run_tests (expect RED). Implement the simplest production code in StringCalculator. run_tests (GREEN). start_refactor if I agree. On GREEN, requirement_mark_implemented. Ask me before each phase change."
Everyone drives this at their own keyboard; you demo REQ-003 (comma-separated numbers) end to end. Show the agent calling validate_spec, then get_requirement (note the featureLocation and workflowHint fields), appending the scenario and the unit test, run_tests RED (8 tests, 3 failing — 2 Cucumber failures + 1 JUnit error), implementation, run_tests GREEN (8 tests), start_refactor, then marking REQ-003 implemented in the spec. Pause after the scenario is written: that's the spec review moment.

The loop you will drive

agentvalidate_spec → the spec (including your new requirement) is valid
agentget_requirement("REQ-003") → acceptance criteria + feature file location
agentscenario_add / unit_test_create — staged; changes_show
youreview staged Gherkin — then allow changes_commit
REDrun_tests → Cucumber + JUnit failures returned to the agent
agentimplements the simplest passing code in StringCalculator
GREENrun_tests → all pass
REFACTORstart_refactor → clean up → run_tests stays green
youapprove; requirement_mark_implemented (GREEN-gated); repeat with REQ-004..006
Call out the two human checkpoints: reviewing the failing test (the spec) and approving the final code. That is "human in the loop" concretely, not as a slogan.

Why this works reliably

  • Valid spec first: validate_spec gates the pipeline — no scenario or code from a broken spec
  • Ground truth: the agent doesn't guess whether code works — run_tests tells it
  • Guardrails in tools: refactor-on-red is impossible; the server refuses
  • Small steps: one requirement, one cycle — failures stay cheap
  • Portable: same bdd mcp serve in Cursor (24 tools), the bundled client, MCP Inspector, and CLI profiles (3–7)
This is the difference between "LLM writes code" and an engineered workflow: feedback loops and enforced invariants.
